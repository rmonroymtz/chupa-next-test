# Social login on Next (Amasty Google and Facebook)

Objective: port the legacy Amasty social login (Google, Facebook) to the Next `/sign-in` and `/create-account`, and the "Cuenta vinculada con" notice to the profile edit, so the four phase 4 urls can move to Next. Branch `feat/social-login` (from `feat/phase-5-account`). Delivery: ask-on-risk. Runner: vitest (`pnpm test`), Playwright local stack (`pnpm test:e2e --project local`).

## Specs

- S1 Buttons. `/sign-in` and `/create-account` show the Magento social buttons (`amSocialLoginButtonConfig { type label url }`) under the form with the legacy separator "o", only when `storeConfig.amsociallogin_general_enabled` is true, `amsociallogin_general_login_position` lists `popup` and at least one button exists. Hidden otherwise, and when the config cannot be read. Staging (2026-11-17): Google and Facebook, position `popup` only. Button urls must be https; plain http only on a local host (L7, review R1-001). The config is read once per 5 minutes per process, a page waits at most 1.5 s for it, and a failed read keeps the last good config (L7, review R3-001).
- S2 Popup sign-in. A click opens `url + "&isAjax=true&generateToken=true"` in a 500×420 popup centered on the window (legacy `useSocButtons`). Magento answers the opener with `postMessage({ result, token, messages, redirect_data })`. On `result === 1` with a token: the server checks the token with Magento, creates the customer cart and merges the guest cart (the same steps as the password sign-in), the browser stores the session in the PWA format (`startSession`) and goes to `from`, else the page's own default (`/my-account` on `/sign-in`, `/order-history` on `/create-account`, as each page's form).
- S3 Message trust (security, beyond the legacy). Only a message whose `event.source` is the popup this page opened and whose `event.origin` is the origin of the button url is read. Every other message is ignored. The legacy listener checks neither. An Amasty answer from the opened popup but another origin is not used and shows the generic error; a popup closed without an answer is forgotten quietly (L7, review R3-002).
- S4 Errors. `result === 0`: the page shows `messages[0]`, or a generic error when there is none. Assumption: `redirect_data.redirectWithError` on `/sign-in` (legacy: switch to the create-account form) sends the browser to `/create-account` keeping `from`. A popup the browser blocks shows an error asking to allow pop-ups.
- S5 Linked accounts notice (user L3, phase 5 O3). On `/my-account/edit-account-information`, when `amSocialLoginAccountData { type name }` returns at least one account, the Security section shows, instead of the password status and "Cambiar contraseña", the legacy block: "Cuenta vinculada con {names joined with ' y '}", "Tu cuenta no tiene contraseña propia establecida. Podemos enviarte un correo para que crees una.", the button "Enviar correo de restablecimiento" ("Enviando..." while sending), on success "✓ Enviamos las instrucciones a {email}. Revisa tu bandeja de entrada y spam.", on failure "No pudimos enviar el correo. Intenta de nuevo.". The email is `requestPasswordResetEmail` with reCAPTCHA `CUSTOMER_FORGOT_PASSWORD`. When the list is empty or cannot be read, the page stays as it is, except that "Cambiar contraseña" appears only once the list is known (legacy).
- S6 Docs. Phase 4 routing and reports say social login is on Next and all four phase 4 rules can go live.
